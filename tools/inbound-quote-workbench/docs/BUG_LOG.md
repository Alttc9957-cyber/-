### BUG-20260703-007

Bug 编号：BUG-20260703-007

发现日期：2026-07-03

发现来源：开发过程 / 自测

问题描述：新增产品备注结构化模块中，`保票政策：保证出票，需二次确认` 同时命中“确认”和“保票”，旧判断顺序先归类为 `booking_policy`，导致保票政策没有进入 `guarantee_policy`。

出现位置：`public/js/domain/product/remark-atoms.js`

1. 调用 `normalizeProductRemarks`。
2. 传入 `rawFields: { 保票政策: "保证出票，需二次确认" }`。

预期结果：包含 `guarantee_policy`。

实际结果：修复前归为 `booking_policy`。

严重程度：低

影响范围：新增备注结构化模块；未影响旧报价主流程。

修复方案：把 `保证|保留|占位|保票|保房` 的判断顺序提前到预约确认之前。

涉及文件：`public/js/domain/product/remark-atoms.js`、`tests/remark-atoms.test.js`

验证步骤：执行 `node --test tests/remark-atoms.test.js` 和 `node --test tests/*.test.js`。

### BUG-20260703-005

Bug 编号：BUG-20260703-005

发现日期：2026-07-03

发现来源：客户反馈 / 开发过程

问题描述：Supabase 云端产品库已建立，但前端产品资源库和报价匹配仍主要读取本地 `state.productCatalog` / localStorage 覆盖层，导致云端底库没有稳定进入产品页和报价明细。旧本地缓存可能把成本为空或为 0 的脏数据重新带回报价。

出现位置：产品资源库页面、`loadSystemProductCatalog`、`loadLocalProductState`、`saveLocalProductState`、`generateQuoteResources`、报价匹配函数。

复现步骤：

1. 发布 Supabase 产品库批次。
2. 浏览器本地塞入旧 `youyixing_product_state`。
3. 刷新页面并生成重庆接机或北京故宫报价。
4. 观察产品页和报价行是否使用云端产品资源。

预期结果：云端批次发布后，产品页和报价资源池优先使用云端产品资源；本地坏缓存不得覆盖云端底库。

实际结果：旧逻辑存在继续读取本地产品库的风险，报价行来源 ID 也可能只是前端临时编号。

严重程度：高

影响范围：产品库可信度、报价成本回填、刷新后的数据稳定性、报价行追溯。

可能原因：B 方案第一阶段只完成云端数据底座和服务端 API，前端读取层尚未接管。

修复方案：系统产品库加载后调用 `/api/product-imports/latest/report` 和 `/api/product-resources`，用云端资源覆盖前端产品库的用车、门票、导游、酒店、餐厅和特色体验；云端启用时忽略旧本地产品库覆盖层；报价资源保留云端资源 UUID。

涉及文件：`app.js`、`server.js`

验证步骤：

1. 打开 `http://127.0.0.1:8787/`，确认 `state.cloudProductCatalog.loaded=true`。
2. 确认云端数量：用车 940、特色体验 77、门票 145、导游 48、酒店 153、餐厅 151。
3. 手动写入坏本地缓存后刷新，确认坏缓存未进入 `state.productCatalog.vehicles`。
4. 生成重庆接机 7 座报价，确认成本 250、供应商“待绑定供应商”、来源资源 UUID 写入报价行。

验证结果：已通过浏览器验收和 API 验收；坏本地缓存未覆盖云端产品库。

当前状态：已修复

### BUG-20260703-007

Bug 编号：BUG-20260703-007

发现日期：2026-07-03

发现来源：开发过程 / 对抗性审查

问题描述：云端产品匹配 API 在同城市、同服务类型、同车型命中时，即使路线不匹配也可能给出 `matched`。重庆市内一日游 8 小时 / 7 座曾错配到重庆武隆 7 座，成本从预期 700 变成 950。

出现位置：`POST /api/product-resources/match`、`productResourceMatchScore()`

复现步骤：

1. 请求 `POST /api/product-resources/match`。
2. body 使用 `{ category:"用车", city:"重庆", serviceType:"包车", model:"7座", route:"市内一日游 8 小时" }`。
3. 查看返回资源。

预期结果：命中 `重庆包车 市内一日游8小时 7座`，成本 700。

实际结果：旧逻辑可能命中 `重庆包车 武隆 7座`，成本 950。

严重程度：高

影响范围：用车报价成本、跨城市 / 多路线报价准确性、客户验收信任。

可能原因：旧评分中城市、品类、服务类型、车型合计可达到 matched 阈值，路线未命中没有降级；同时未处理“市内一日游 8 小时”和“市内一日游8小时”的空格差异。

修复方案：增加路线归一化和关键词同义族；当请求包含明确路线时，路线不命中最高只能进入待确认，不能直接 matched。

涉及文件：`server.js`、`tests/product-resource-match-scoring.test.js`

验证步骤：

1. 执行 `node --test tests/*.test.js`。
2. 重启 8787 服务。
3. 分别请求重庆接机、送机、武隆包车、市内一日游四个用车用例。

验证结果：31 项测试通过；重庆接机 / 送机 7 座返回 250，重庆武隆包车 14座~17座返回 1500，重庆市内一日游 8 小时 7 座返回 700。

当前状态：已修复

### BUG-20260703-008

Bug 编号：BUG-20260703-008

发现日期：2026-07-03

发现来源：客户反馈

问题描述：报价明细成本输入框下方直接展示完整来源、候选资源和失败原因，导致报价页面备注过长，客户测试时难以聚焦价格本身。

出现位置：`sourceNote()`、用车分段展示、报价明细表。

复现步骤：

1. 生成一份含缺成本或多候选的报价。
2. 查看报价明细成本输入框下方。
3. 观察是否出现长串“待补价 / 候选资源 / 匹配失败原因”。

预期结果：默认只显示短状态，例如产品库成本、待确认、待补成本、未匹配；完整原因在内部诊断或折叠详情中查看。

实际结果：旧逻辑直接将来源、候选和原因全部铺在报价行内。

严重程度：中

影响范围：客户演示观感、报价人员检查效率、页面可读性。

可能原因：`sourceNote()` 同时承担客户可见提示和内部诊断，缺少展示分层。

修复方案：新增 `quote-display.js` 统一压缩来源状态；`sourceNote()` 改为短标签 + 折叠详情；新增报价诊断面板保存完整来源、候选和原因。

涉及文件：`app.js`、`styles.css`、`public/js/domain/quote/quote-display.js`、`tests/quote-display.test.js`

验证步骤：

1. 执行 `node --test tests/*.test.js`。
2. 浏览器生成报价，确认报价行默认不再出现“候选资源：”长文案。
3. 查看折叠诊断面板，确认仍可看到匹配状态和原因。

验证结果：31 项测试通过；浏览器 smoke check 确认短标签出现，默认正文不再出现“候选资源：”，诊断面板可输出状态和原因。

当前状态：已修复
